# Datasheet — GEM (Game Engine Migration) v0.1

Following Gebru et al., *Datasheets for Datasets*. Every count in this
document lives in `v0.1/summary.json`, generated by `miner/derive.py`
from the measured tables; none is transcribed by hand.

---

## Motivation

**Why was it created?** Game engines ship breaking major versions, and
projects must either migrate or stay behind. No public dataset records
when open-source game projects actually made that move, what it cost, or
what evidence exists that anything was blocked while they waited. A
novelty sweep across DBLP, Crossref/ACM, Crossref/IEEE, OpenAlex,
Semantic Scholar, and a manual census of 42 GAS@ICSE papers 2022–2026
returned no study of game-engine version migration
(`../search_protocol.md`, run 2026-08-19).

**What gap does it fill?** Technical-lag research measures distance from
the latest release. It does not measure whether that distance costs
anything. GEM records lag, cost, and blocked demand as three separate
observables so the relationship between them can be tested rather than
assumed.

**Who created it?** Compiled at UFRJ as the empirical basis for three
papers: a dataset and tool showcase, a study of whether engine version
lag constitutes technical debt, and a study of what automated migration
cannot do.

---

## Composition

**What do instances represent?** Several linked entity types, documented
in `SCHEMA.md`: engine releases, repositories, project files, declared
versions over time, version-change events, migration windows, churn,
branches, SATD counts, blocked-demand signals, strata labels, agreement
checks, and derived survival observations.

**Is any of it missing, and is the absence meaningful?** Yes, and the
distinction matters:

- **Godot 3.x minor versions do not exist in the data.** A Godot 3
  `project.godot` declares `config_version=4` and nothing finer. This is
  a property of the file format, not missing data, and must not be
  imputed. Minor-granularity lag is a 4.x-era measure only.
- **Repositories with no independent version signal** are recorded as
  `no-secondary-signal` in `validation`, kept separate from `agree`.
- **Branches deleted after merge** leave no trace, so `branches` counts
  are lower bounds.
- **Failed fetches leave gaps**, never substituted values. A batch that
  fails is logged and left as a gap.

**Does it contain data relating to people?** Yes, in `blocked_demand`:
public issue and pull-request URLs, titles, dates, and a flag for
whether the author was a maintainer. **Author handles are stripped from
the released tables** and retained only in `evidence/ledger.jsonl`, which
is not distributed. See *Ethics* below.

**Is it a sample or a census?** A sample, at three tiers, and the tier of
every repository is recorded:

| Tier | What it holds | Cost per repo |
|---|---|---|
| **Frame** | GitHub metadata for every non-fork repository matching `topic:godot`, `topic:godot-engine`, or `language:GDScript`, created before 4.0-stable | ~0 |
| **Snapshot** | Full default-branch tree, every `project.godot` path, and the declared version | 1 API call |
| **History** | Blobless-filtered clone, complete version-event history, churn, branches, SATD | 1 clone |

The frame is enumerated exhaustively by bisecting each query on
`created:` until every slice is under GitHub's 1,000-result retrieval
cap (caveat C2). The snapshot and history tiers are subsets, and the
selection rule for each is recorded in `summary.json` rather than left
implicit.

**Are there errors or redundancies?** GitHub search `total_count` values
are approximate, include forks and vendored copies, and drift between
runs (C1) — one query returned 10,718 on 2026-08-19 and 10,839 on
2026-08-25. Counts derived from enumerated rows do not have this
problem; counts quoted from `total_count` do, and are tiered `REPORTED`
in the evidence ledger, never `MEASURED`.

## Collection process

**How was the data acquired?** Three mechanisms, all recorded:

1. **GitHub REST API** for release timelines, repository metadata, trees,
   and issue search.
2. **`raw.githubusercontent.com`** for file bodies, which does not
   consume the core rate limit and is what makes the snapshot tier
   affordable.
3. **Local git** over size-filtered clones for version history, churn,
   branches, and SATD.

**Detection method, and why not the obvious one.** Version events are
found by reading `project.godot` at every commit that touched it and
comparing against the first parent — never by searching commit messages.
The motivating case is Thrive's Godot 3→4 boundary commit `217ef43e`,
whose subject is *"Project file upgrades"*: it names neither the engine,
nor a version, nor a migration, and is invisible to a message search
(caveat C5). The same pattern recurs — `godot_heightmap_plugin`'s two
major migrations are titled *"Update to use global class names"* and
*"New project.godot format"*. Every event therefore carries three flags
recording whether its subject named the engine, a version, or a
migration, which converts that anecdote into a measured miss rate.

**Why a size-filtered clone rather than a blobless one.** A blobless
clone (`--filter=blob:none`) defers every file body to a lazy fetch, and
git issues one network round trip per object even under
`git cat-file --batch` — measured at roughly 0.55 s per blob, which
makes reading a file at every commit unaffordable. `--filter=blob:limit=256k`
brings the entire text history down in the initial pack while leaving art
and audio behind. On one repository the same bulk read went from 7.2 s to
0.004 s.

**Over what timeframe?** Repository state was collected in August 2026;
the histories it draws on run from 2014 to the collection date. Every
row carries its own collection date, and the snapshot table is designed
so re-running appends a new observation rather than overwriting, turning
the corpus into a panel.

**Was it validated?** Yes, and the result gates everything downstream. A
declared version is a claim a project makes about itself, not a
measurement of the engine in use (caveat C9). `miner/build_validation.py`
compares it against CI pins, container tags, export presets, and README
badges, and reports the agreement rate with `no-secondary-signal` counted
separately from `agree` — folding those together would inflate agreement
with every project that has no CI.

**Ethics.** Issue-tracker content is human-subject data. Handles and
permalinks stay in the ledger; the released tables carry the URL and the
title but not the handle. Quoting any individual requires UFRJ CEP
clearance and has not been sought for v0.1; aggregate counts do not
require it. Issue-tracker evidence over-represents organised teams —
solo developers who migrated, or decided not to, in silence leave no
record at all (caveat C7).

## Preprocessing and labelling

**What is raw and what is derived?** `releases`, `repos`,
`repo_signals`, `project_files`, `snapshots`, `dependencies`,
`version_events`, `migration_windows`, `churn`, `branches`, `satd`,
`repo_history`, and `validation` are measured. `strata`,
`blocked_demand`, and `lag_observations` are derived or rule-labelled. Deleting every derived table and re-running
`miner/derive.py` must be a no-op.

**Are the labels ground truth?** No. `strata` and `blocked_demand` carry
`method="rule"` and `coder="rule-v0.1"`. They are candidate labels
intended to make a manual pass affordable, not to replace it. **A
two-coder manually adjudicated subsample with a reported κ is required
before either carries a published figure.**

The two rule sets are also not tuned the same way, and pooling them
would mislead. The demand rules favour recall and the counter-demand
rule favours precision, so any in-debt fraction computed from the labels
alone is an **upper** bound, not an estimate. Every
`blocked_demand` row carries `confidence`; the weakest tier requires the
version token in the issue title precisely because an earlier version,
which accepted it anywhere in the body, labelled ordinary bug reports as
migration blockers. The `method` and `coder`
columns exist so that a consumer can tell rule labels from adjudicated
ones, and so adjudicated labels can be merged in later without
rewriting history.

**Is the raw data retained?** Yes. Every table row cites `ev_id`, the id
of a content-addressed artifact in `evidence/ledger.jsonl` recording the
exact command or URL that produced it, its SHA-256, and its byte length.
`miner/check.py` fails the build on a row without provenance or citing
an id absent from the ledger.

## Uses

**What is it for?**

- Descriptive migration timelines and survival curves with
  right-censoring for the never-migrated — averaging over migrators
  alone conditions on the event having happened and understates the wait.
- Testing whether migration cost grows with lag duration, controlling
  for project size (`churn` against `lag_observations`).
- Measuring what carrying two engine versions in parallel costs
  (`branches`).
- Testing whether repayment trades version debt for code debt
  (`satd` across the migration window).
- Selecting pre-migration trees as input to
  `godot --validate-conversion-3to4`, with the post-migration tree as
  human ground truth.

**What should it not be used for?**

- **Do not read lag as debt.** Lag is a version number. The dataset
  deliberately keeps lag, cost, and blocked demand as three separate
  observables precisely so the link between them stays testable.
- **Do not treat "behind latest" as "unsupported."** `3.6.3-stable`
  shipped 2026-08-22, three years and five months after `4.0-stable` and
  two months after `4.7-stable`. A project on Godot 3.6 is on a line
  upstream is actively patching. `lag_observations.still_supported`
  exists to keep that distinction available.
- **Do not pool strata.** Tooling migrated onto 4.0 betas in 2022; games
  migrated in 2024. A mean over both describes neither.
- **Do not pool window rules.** `branch-merge`, `commit-burst`, and
  `single-commit` windows are not equally reliable, and a `saturated`
  window hit a bound rather than finding a natural edge.
- **Do not generalise past GitHub, past open source, or past one
  engine.** The schema is engine-agnostic and carries adapters sketched
  for Unity and Unreal, but only Godot is instantiated in v0.1.

## Distribution and maintenance

**How is it distributed?** JSONL tables plus tree manifests, archived to
Zenodo with a DOI at submission. Tree tarballs are included only where
the repository license permits redistribution; the `(repo_id, sha)` pair
makes any tree reconstructible from a clone, though reconstruction fails
for repositories later force-pushed or deleted, which is why the subset
is archived rather than merely referenced.

**License.** The dataset records public metadata and derived measures.
Where file content is redistributed, the source repository's license is
recorded per row and content is included only when that license permits
it. Rows with `license: null` are excluded from any content
redistribution.

**Will it be updated?** The snapshot table appends rather than
overwrites, so re-running extends the panel. `search_protocol.md` and
`ev.py protocol` regenerate the exact query log for a re-run and diff.
